# 项目开发卡 v2：创作与守护交接约定

## 读取与更新

- 采用下面的固定分区；使用 assets/project-card.md 生成可阅读的卡。用户只要简短答案时，允许精简排版，但保留约束、来源/虚构边界、故事核心和选定状态。
- 保持同一项目ID；首次使用可用简短项目代号。每次修改将修订号加一；不得假称历史版本已保存。
- 读取用户提供的最新卡和明确指令；以本轮指令优先。缺失字段写“未指定”，未知事实写“未核实”；不要补造来源、工具能力、时长或预算。
- 用户给出旧格式、普通梗概或不完整卡时，直接规范化可用信息，不因格式缺失中止工作。
- “推荐”与“用户选定”分开记录。只请求选材时，交付推荐后结束；用户指定候选才标为“用户选定”。已授权“选材并写剧本”而未指定候选时，可标“按推荐暂定”，接着写作并说明假设。
- 写剧本时保留选材约束、来源编号与核心设定。用户只改一个部分时，仅更新相关内容及受影响的连续性事实。
- 多项目对比为每个候选保持独立卡；“第3个”只从当前可见列表解析，不把不同批次的序号混用。
- 不暗示卡会跨会话自动记忆。跨会话继续时读取用户选中的文件或粘贴内容；确实已保存时给出实际保存入口。

## 固定分区及字段

| 分区 | 必须保留的内容 |
| --- | --- |
| 元信息 | 格式版本v2、项目ID、修订号、标题、入口模式（热点/原创/素材）、选定状态；已有v1卡继续读取，转换时保留原件 |
| 项目条件 | 短片/连续短剧、目标时长或每集时长与集数、受众、语言、地区/时区、画幅、视觉风格、制作条件；注明哪些来自用户、哪些为默认假设 |
| 来源与事实 | 联网状态及检索时间、检索窗口、覆盖范围；来源编号、标题、URL、报道时间、事件时间、读取状态；已核实事实、未核实内容、可见热度依据 |
| 创作转化 | 核心观众情绪、人物困境、事实启发点、虚构人物/情节/世界规则、与真实事件的区别 |
| 故事核心 | 一句话故事、主角目标、阻力、关键选择、代价、独特卖点、主题方向 |
| 结构承诺 | 短片：开场/五节点/结尾回收；短剧：持续冲突机制/人物关系升级/前三集概念/阶段结局/目标集数支撑 |
| 制作计划 | 主要人物和场景、三个关键场面、可复用资产、难点、保留戏剧作用的替代表现、工具能力未知项 |
| 选材判断 | 故事吸引力与制作可行性分别评分及依据、置信度、开发建议、主要待验证点；用户未要求选材评估时允许写“不适用” |
| 连续性与进度 | 已锁定设定、人物已知信息、时间线、伏笔及回收、已完成范围、未完成范围、本轮修改、下一步 |

## 事实与创作的边界

- 将来源的支持范围限定到真正读到的内容；摘要或用户转述不等于全文核实。
- 只在来源确实给出数据时记录排名、讨论量或阅读量，并写清平台与时间口径；不能跨平台直接加总为“全网热度”。
- 原创模式注明“原创构思，未检索热点”；素材模式标注实际已读范围。
- 让故事主张来自人物行动和剧情，不把虚构对话、动机或结局回填为来源事实。
- 没有授权信息时不声称素材已获改编授权；只在任务需要时记录用户提供的授权情况。

## 制作能力记录

按用户当前工具、已验证样片、现有角色/场景资产和人工后期能力记录。未知能力保持未知。分别记录群体互动、口型/配音、持续身份、复杂动作、细节道具、视觉奇观等关键需求，避免把某种题材永久列为禁用。

## 交接方式

- 用户只选材：给候选对比、推荐卡和可直接继续的写作入口。
- 用户已指定写作：读取卡中的选定状态和项目条件，继续 write-screenplay；若当前宿主没有可调用的 Skill API，读取可用的对应 SKILL.md 并执行其流程，不声称调用了不存在的接口。
- 用户直接写剧本：由 write-screenplay 创建或更新卡，不强制经过 select-story。
- 发现问题：先给具体修复；涉及主角身份、核心世界规则或用户锁定结局的变动时，保留原方案并提出变体，遵从用户授权范围。

## 本地 MCP 与专职 Agent

持续项目同时记录 project_root、MCP revision、原稿 ID 和登记 hash。项目卡是可阅读的交接材料，`.story-studio/state.json` 与真实原稿提供最新定位；不得让旧卡覆盖新正文。

story-keeper 维护约束、人物、知情范围、伏笔与索引，只返回修订意见。写作 Agent 修改正文并登记版本，守护者再核对证据。记录 data 可扩展，不用固定表格限制项目需要。

每次场次/单集或阶段完成保存检查点；恢复先核对版本与原稿。请求全稿时，确认全部范围完成、必回收伏笔闭环和当前语义审查通过后定稿。旧卡缺技术字段不算剧本质量问题。
