# 剧本编写

把故事写成具有行动、选择和后果的电影文字，交付能继续制作的剧本。遵循用户最新要求、已确认项目开发卡与已有正文；按当前阶段接续，不要求先运行选材 Skill，也不默认联网。

## 读取资源

- 开始时读取 [项目交接约定](references/project-contract.md)，核对项目、版本、硬约束、来源事实与虚构设定。
- 新建或更新开发卡时使用 [项目开发卡](assets/project-card.md)。只有明确需要新方向或选材比较时才接入 `select-story`。
- 构思与调整结构时读取 [戏剧结构](references/dramatic-structure.md)。
- 需要类型化表达、人物深化或台词修订时读取 [类型与人物对白方法](references/genre-and-dialogue.md)，仅使用适合当前项目的方法。
- 写正文和估算时长时读取 [剧本格式](references/screenplay-format.md)。
- 完稿、改编或修订时读取 [修订检查](references/revision-checklist.md)。
- 文件交付时可复制 [剧本模板](assets/screenplay.md)；连载或分批工作同时维护 [连续性档案](assets/series-continuity.md)。按任务删去不用的栏目，替换全部占位符。

## 1. 对齐输入与范围

1. 读取用户提供的开发卡、正文、梗概和制作条件，识别任务是新写、改编、扩写、续写还是修订。直接引用现有事实和约束，不把自己的推断写成已确认条件。
   已初始化 MCP 项目时先调用 `studio_recover_project`；对恢复入口、陈旧索引或多次上下文压缩后的任务，委派本项目的 `story-keeper` 核对相关原稿。不能用聊天摘要替换最新正文。
2. 列出必须保留的核心：故事前提、主要人物、结局、类型与风格、时长或集数、来源边界、已完成情节。用户允许重构时按授权修改。
3. 缺少非关键参数时在开头简短说明假设并继续。直接写短片而未指定条件，默认原创、约3分钟、写实风格；明确写连续短剧但未指定规模，默认6集、每集约90秒。已有项目卡、正文和用户设定均优先于默认。
4. 用户只给主题时创作原创故事；只给大纲时从场景或分集开始；已有正文时从指定修改范围开始。不要重复每一步确认，也不要把用户要的完整剧本缩成提案。
5. 必要背景以已有资料为准。用户要求查证或任务依赖当前事实才搜索，记录来源与时间。不要凭空补充近期热点、热度数据、真实人物言行或事件细节。
6. 只有互相矛盾且无法兼容的硬约束需要澄清。先推进不依赖答案的部分；对一般逻辑缺口直接提出并采用保留核心设定的具体修复。

创建或更新开发卡时保留固定分区与项目ID，修订号逐次递增。直接写作的选材判断可填“不适用”；原创未搜索时写“原创构思，未检索热点”。遵循卡中的选定状态，不能将推荐写成用户选定。未指定字段和工具能力保持未知，不冒充自动跨会话记忆。

## 2. 建立人物与核心冲突

用少量人物构建清晰关系，逐一确定：

- 想要什么，以及为什么必须现在行动。
- 谁或什么阻止目标，阻力怎样随行动改变。
- 面临什么两难选择，各选项的代价是什么。
- 最终做出什么行动，结果怎样体现变化或拒绝变化。

让关键剧情由人物行动和决定推动。环境、偶然事件或反派可以制造问题，不能在结尾无铺垫地代替主角解决问题。给主要人物不同的知识、利益、说话习惯和行动策略。

## 3. 推进故事结构

### 独立短片

- 围绕一个核心问题安排开场、触发、尝试与升级、关键选择、结果与回收。
- 用画面和行动建立信息，限制需要额外解释的规则与关系。
- 结尾兑现主要冲突和情绪承诺；开放结局也要让关键选择产生可见结果。
- 一个反转必须改变对先前信息的理解，并能追溯到已出现的线索。

### 连续短剧

- 先确定全季主目标、持续冲突来源、角色关系变化、阶段回收与季终结果，再规划分集。
- 每集写清开局处境、具体目标、阻力、选择、新结果以及留给下一集的问题。
- 每集交付至少一次实际变化或情绪回报，让下一集由后果自然产生。
- 升级可来自代价、信息、关系或局势变化；不要仅反复误会、增加同类对手或截断当前场景。
- 在整个季的时间线与设定上核对新增情节，避免为当集效果改写前文规则。

有严重逻辑问题时说明影响，给出能保留项目核心的修复并继续。只有任务本身要求重新选题、或核心无法成立而需要用户决定方向时才返回选材阶段；不得静默替换核心前提、主要人物或既定结局。

## 4. 拆成场景或分集

1. 给每场安排人物目标、可见阻力、动作变化与离场后的新局面。合并功能重复的场景，删去既不改变局面也不建立必要信息的段落。
2. 先分配场景或分集时长预算，再写正文；把对白、反应、动作、转场与留白都计入。目标时长按用户要求执行，超过预算时压缩或重排，不能仅把标注时长改小。
3. 保持角色、地点、服装、道具与规则的连续性。制作条件是边界，创意价值是目标；不为简化制作消除必要冲突。
4. 对关键困难场面设计可执行替代，例如通过结果、声画关系、局部动作或人物反应表达；保持该场面的信息、压力和人物选择。
5. 不绑定具体生成模型、镜头秒数或技术规格。只有用户要求分镜或提示词时另行生成，不用提示词替代剧本。

## 5. 写完整正文

- 固定默认使用 [中文文学剧本格式](references/screenplay-format.md)：书名号标题、剧名/主题/频类/题材、正文、中文集标题、`1-1地点日/内` 场标题和人物表。动作以 `△` 开头，对白用 `人物名（必要提示）：台词` 同段表达；不自行切回 INT./EXT. 或人物名与对白分段。用户明确指定的新格式优先。
- 动作用现在时写可被看见、听见或由表演体现的内容。心理活动改成行为、停顿、目光、道具使用或必要对白。
- 对白标明说话人；只在语义或表演容易误解时加简短提示。声音标明来源，画外音、电话和旁白与现场对白区分。
- 让对白承担行动、试探、隐瞒或关系变化；避免所有人物同一种口吻，以及向观众重复已经明确的画面信息。
- 保留用户要求的类型与情绪风格，不套固定爽点、反转或开场秒数。
- 修订任务交付修订后正文，简要列出实质变化；用户要求评论或问题清单时按其范围输出，不擅自重写。

## 6. 自查、修订与交付

依照修订检查完成一轮自查，修复因果、动机、信息可见性、时间线、伏笔、对白差异与时长问题，再交付。只向用户展示结论、正文和必要说明，不夹入内部思考过程。

### 专职伏笔与记忆 Agent

在已初始化的项目中，按当前宿主支持的子 Agent 机制委派 `story-keeper`；给它 project_root、本次任务、读取到的 revision、原稿 ID 和用户决定。长稿按场次/单集完成、核心设定变更、阶段结束及终稿前委派，不在每句对白后调度。

- 写作 Agent 是正文唯一修改者。先保存正文，再用 `studio_register_document` 登记新版本；旧证据需要守护 Agent 检查并重新定位。
- 守护 Agent 只维护记忆与索引、返回审查意见。接收具体问题后修订正文，再委派复核；不要用“工具通过”替代剧情判断。
- 前期保存人物欲望、世界规则和伏笔计划；已埋设或已回收必须引用真实正文。必回收伏笔不得为了过检查而自动取消或延期。
- 完成阶段后保存 `studio_save_checkpoint`。摘要列出版本、当前处境、任务和下一步；事实详情通过记录 ID 与原稿定位读取。
- 全稿完成后由守护 Agent 提交当前版本的 `studio_submit_review`；修订后旧审查失效。确认所有请求集数已完成，再调用 `studio_finalize_project`，最后保存定稿检查点。

若角色、MCP 或子 Agent 机制不可用，准确报告缺口，使用可用材料推进授权写作；不得声称已经运行专职 Agent、自动持久化或完成定稿检查。需要初始化时读取同插件 `setup-story-project/SKILL.md`。仅点评、构思或无持久化条件的短任务不强制启动项目服务。

默认交付：

1. 极简项目说明：采用的目标与必要假设；接续已有卡时注明版本。
2. 用户需要的人物与大纲或分集规划；用户只要正文时省略这些过程材料。
3. 完整剧本正文，按场次或集数组织。
4. 简短制作检查：角色/场景资产、关键难点与替代、预计时长；标明时长为估算，实拍、表演或剪辑仍需校准。
5. 更新项目开发卡中的决定、版本、状态与下一步；连载同时更新连续性档案。

请求全集时完成指定全集，不能把第1集或示范场当成全稿。长稿优先以文件交付完整正文；确需分批时先明确总集数、每集目标、已完成范围与剩余范围，保存全季结构、人物状态、线索账本和下一批入口，持续推进并准确标注“本批”，不得宣称全集完成。

文件格式遵循用户要求；保存和交付调用当前环境的文件或文档技能。不要写入已安装 Skill 的模板目录。生成文档时使用相应文档技能验证排版。
